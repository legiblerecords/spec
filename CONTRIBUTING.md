# Contributing

Legible Records is a draft. Issues are welcome: questions, problems with the spec, and types you'd like to publish. Pull requests are welcome too, but for anything beyond a fix, open an issue first so we can agree on the change.

## Sign your commits off

Contributions are accepted under the [Developer Certificate of Origin](https://developercertificate.org/). Add a `Signed-off-by` line to every commit (`git commit -s`), certifying that you wrote the change or have the right to contribute it under the license of the part it changes: CC BY 4.0 for the spec's text and the site's guides, CC0 for schemas, fixtures and vectors, Apache 2.0 for code (see [License](README.md#license)).

## Changing the spec

- A change to a published type's schema must follow [the compatibility rules](spec/rules.md#compatible-changes), and comes with fixtures: at least one valid record that uses the change, and an invalid one when the change adds a constraint.
- A change to the schema language or restricted YAML comes with vectors: a case for each new rule, and an error case for each new problem.
- The signature, key-set, bundle and feed vectors are generated by `scripts/make_vectors.py` and never edited by hand: change the generator, run `python scripts/make_vectors.py`, and commit what it writes. `scripts/check_vectors.py` re-checks every vector under rules written independently of the generator, in the order the prose gives; a new rule goes into both, and into the prose first.
- Run these before opening a pull request. CI runs them too.
  - `python scripts/check_fixtures.py`
  - `python scripts/check_vectors.py`
  - `python scripts/make_vectors.py --check`, which fails if a committed vector differs from what the generator writes
  - `python scripts/check_mutations.py`, which disables checks in `check_vectors.py` one at a time and fails unless the vectors then catch it
- A change to `spec/` or `schemas/` is published on the [site](site/), which CI builds and checks: in `site/`, run `npm ci` and `npm run check`. It fails on a link to a missing page or section, such as a heading a guide links to that the change renamed, and on a schema not served at its `$id`. Update a guide the change makes wrong in the same pull request.
- Keep the expanded `v<n>.json` and the short-form `v<n>.yaml` of a schema in step. The JSON is what `legible expand <yaml> --base https://legiblerecords.org/schemas/` writes from the YAML, byte for byte.

## Publishing your own types

You don't need to contribute here to publish types. Publish them under a domain you control, following the spec, with your own fixtures. Open an issue if you'd like them listed.
